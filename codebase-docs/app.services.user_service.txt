[ PLAIN ENGLISH ]
This is the brains for users: find a user by email, create a new user (scrambling
their password first), and check a login attempt. Deactivated accounts are
rejected at login with a clear signal.

[ TECHNICAL ]
Business logic over the User model; uses core.security for hashing/verify.

[ METHODS / SYMBOLS ]
- get_user_by_email(db, email) -> User | None  (async)
    Plain: Look up a user by email.
    Tech:  SELECT User WHERE email == email; first() or None.
- create_user(db, user_in) -> User  (async)
    Plain: Create an account with a scrambled password.
    Tech:  hashes password, adds User(email, hashed_password, role), commit,
           refresh, return.
- authenticate_user(db, email, password) -> User | None  (async)
    Plain: Verify a login; None if wrong, error if deactivated.
    Tech:  None if no user or bad password; raises InactiveUserError if
           not is_active; else returns the user.
- InactiveUserError (Exception)
    Plain: Signal that the account is deactivated.
    Tech:  raised by authenticate_user; mapped to HTTP 403 in auth_routes.

[ READS / WRITES / LOGS ]
Reads/Writes: users table. No direct logs.

[ RELATIONS ]
Called by: controllers.auth_routes, controllers.user_routes,
           api.dependencies (get_current_user), middleware (id lookup).
Calls:     models.user_model, schemas.user_schema, core.security.

[ NOTES / GOTCHAS ]
Returning None for both "no user" and "wrong password" is intentional — callers
surface one generic 401 so attackers can't tell which failed.
