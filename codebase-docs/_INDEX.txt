PURPOSE
-------
This folder is a plain-text, human-and-machine-readable mirror of the codebase.
For every source file there is one .txt doc here describing what the file is,
what its methods do, what it reads/writes/logs, and how it connects to the rest
of the system. Each doc is written for TWO audiences at once:

    [ PLAIN ENGLISH ]  — a non-engineer can understand what this is and why.
    [ TECHNICAL ]      — an engineer gets the precise behavior and contracts.

These docs are documentation, not source of truth for layout — that remains
`structures.txt` at the repo root. Think of it this way:
    structures.txt  = the MAP   (where files live, naming rules)
    codebase-docs/  = the GUIDE (what each file actually does, in depth)

Two non-file "meta" docs head this folder:
    _INDEX.txt      = this file: the maintenance protocol, template, and file map.
    _KNOWLEDGE.txt  = the PRIMER: the cross-cutting concepts, tech stack, auth &
                      security model, and patterns that span many files. Read it
                      to understand the system as a whole; keep its sections in
                      sync when a concept (not just one file) changes.


--------------------------------------------------------------------------------
MAINTENANCE PROTOCOL  (instructions for Claude / any AI assistant)
--------------------------------------------------------------------------------
Treat this folder as a living artifact. Whenever you create, modify, move,
rename, or delete a source file under `app/` or `tests/`, you MUST keep its
matching doc here in sync IN THE SAME CHANGE:

  1. CREATE a source file  -> create its .txt doc here (see NAMING below).
  2. CHANGE a method/route/model/log -> update the affected section(s):
        [ METHODS / SYMBOLS ], [ READS / WRITES / LOGS ], [ RELATIONS ].
  3. DELETE/RENAME a source file -> delete/rename its doc to match.
  4. Always refresh the LAST-SYNCED date at the top of any doc you touch.
  5. If you add a brand-new layer/folder, also update this _INDEX.txt file map
     and `structures.txt`.

Keep both audiences accurate: if you change technical behavior, also fix the
PLAIN ENGLISH summary so the two never disagree. Do not let a doc describe
behavior the code no longer has — a wrong doc is worse than a missing one.


--------------------------------------------------------------------------------
NAMING
--------------------------------------------------------------------------------
One doc per source file. The doc name is the source file's module path with
dots, plus `.txt`. Examples:

    app/core/middleware.py            ->  app.core.middleware.txt
    app/api/controllers/auth_routes.py->  app.api.controllers.auth_routes.txt
    tests/conftest.py                 ->  tests.conftest.txt
